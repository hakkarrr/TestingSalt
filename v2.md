### Task 2a.1 — Local Message Rendering (Client-Side Only)

**Goal:** Clicking "Send" or pressing Enter creates a new message bubble on the screen, purely in JavaScript (no database yet).

**Action Steps:**

1. In `script.js`, write a function `createMessageBubble(text, isSent)` that:
   - Creates a `<div>` with class `message`.
   - Adds class `sent` or `received` based on `isSent`.
   - Sets the inner text (use `textContent`, not `innerHTML` for safety).
   - Adds a timestamp span with the current time (use `new Date().toLocaleTimeString()`).
   - Appends the bubble to the `.messages` container.

2. Write an `addMessage(text, isSent)` function that calls `createMessageBubble` and then auto-scrolls to the bottom:
   - `messagesContainer.scrollTop = messagesContainer.scrollHeight`

3. Add an event listener to the **Send button** (`click` event).
   - Read the input value (`input.value`).
   - Trim whitespace. If empty, do nothing (`return`).
   - Call `addMessage(input.value, true)` (sent).
   - Clear the input field (`input.value = ''`).
   - Focus back on the input (`input.focus()`).

4. Add a `keydown` event listener to the **input field**.
   - If `event.key === 'Enter'` and `!event.shiftKey`, trigger the same send logic.
   - Call `event.preventDefault()` to prevent a newline in the input.

5. Add a few hardcoded "received" messages on page load to test the scrolling:
   - In a `window.onload` or just at the bottom of your script, call `addMessage('Hey! Welcome!', false)` and `addMessage('How are you?', false)`.

**Verification (MANDATORY):**
- [ ] Clicking Send adds a green (sent) bubble to the list.
- [ ] Pressing Enter adds a green (sent) bubble to the list.
- [ ] The input clears after sending.
- [ ] The list auto-scrolls to the bottom (scrollbar moves down).
- [ ] The hardcoded messages appear on page load (grey/received).
- [ ] Refreshing the page **loses all messages** (expected — no DB yet).

**If this fails →** Check your selectors (`querySelector` for input, button, container). Ensure `scrollTop` assignment is correct.  
**If this passes →** Proceed to Task 2a.2.

### Task 2a.3 — Connect Vanilla JS to Supabase (Read & Write)

**Goal:** Your page can read existing messages from Supabase on load and write new messages to Supabase when you send.

**Action Steps:**

1. In `script.js`, write an `async` function `fetchMessages()` that:
   - Calls `supabaseClient.from('messages').select('*').order('created_at', { ascending: true })`.
   - Checks the `error` object. If error, log it and return empty array.
   - Returns the `data` array.

2. Write an `async` function `sendMessageToDb(username, text)` that:
   - Calls `supabaseClient.from('messages').insert({ username: username, text: text })`.
   - Checks the `error` object. If error, log it and return `false`.
   - Returns `true` on success.

3. Modify your existing **send handler** (from Task 2a.1):
   - When the user clicks Send or presses Enter, **do not** render the bubble immediately yet.
   - Call `sendMessageToDb('Guest', input.value)` first.
   - If it succeeds (returns `true`), **then** call your `addMessage()` function to render it.
   - If it fails, show a simple `alert('Failed to send. Check console.')`.
   - *(You'll handle this more gracefully later — this is just to test)*.

4. On page load (`window.onload` or script bottom), call `fetchMessages()` and render **all** returned messages using your `addMessage(text, false)` function (but you need to track sent vs received — since there's no auth yet, just render them all as "received" for now, or determine based on a hardcoded "Guest" vs "Other").

**Verification (MANDATORY):**

- [ ] Refreshing the page shows the new message (persisted).
- [ ] **Open two tabs side-by-side.** Send a message in Tab A. Refresh Tab B — the message appears.

### Task 2a.4 — Realtime Subscriptions (Live Sync)

**Goal:** Messages appear in Tab B **instantly** without refreshing, using Supabase Realtime.

**Action Steps:**

1. In the Supabase dashboard, go to **Database → Replication**.
2. Find your `messages` table and **toggle Realtime ON** for it.
3. In `script.js`, write a function `subscribeToMessages()` that:
   - Creates a channel: `supabaseClient.channel('messages-channel')`.
   - Listens for `INSERT` events on the `messages` table.
   - When an insert happens, the callback receives a `payload`. The new message is in `payload.new`.
   - In the callback, call your `addMessage(payload.new.text, false)` (or check if `payload.new.username` matches a logged-in user later).

**The exact subscribe syntax (copy this, it's non-obvious):**

```javascript
function subscribeToMessages() {
    const channel = supabaseClient
        .channel('messages-channel')
        .on(
            'postgres_changes',
            {
                event: 'INSERT',
                schema: 'public',
                table: 'messages'
            },
            (payload) => {
                // This runs when a new message arrives from ANY source
                console.log('New message received:', payload.new);
                addMessage(payload.new.text, false);
            }
        )
        .subscribe((status) => {
            console.log('Subscription status:', status);
        });

    return channel; // So you can unsubscribe later
}
```

4. Call `subscribeToMessages()` on page load (after fetching initial history).
5. **Now address the duplicate bubble problem:**
   - When YOU send a message, `sendMessageToDb` inserts it. Then the realtime subscription fires and also adds it.
   - To fix this, decide on a strategy:
     - **Option A (Easiest):** Don't render optimistically. Only render messages from the realtime subscription. Your send function just writes to DB, and the subscription handles the UI update. (This introduces a slight delay but guarantees no duplicates).
     - **Option B (More polished):** Render immediately (optimistic UI), and in the subscription callback, check if the message matches your most recently sent message (by comparing timestamp or text) and skip it.
   - **Start with Option A** for simplicity. Modify your send handler: remove the `addMessage` call. The bubble will appear when the realtime event fires.

6. Test with two tabs open side-by-side.

**Verification (MANDATORY):**
- [ ] Sending a message in Tab A appears in Tab B **instantly** (within 1 second) **without** refreshing.
- [ ] No duplicate bubbles appear in either tab (you fixed the duplicate issue).
- [ ] The console logs "New message received" for every message sent.

**If this fails →** Check Replication settings in Supabase dashboard. Ensure the channel name is unique. Check the subscription status log.  
**If this passes →** Proceed to Task 2a.5.

### Task 2a.5 — Loading, Error, and Empty States

**Goal:** The UI gracefully handles loading, errors, and empty chat history.

**Action Steps:**

2. **Empty State:**
   - After `fetchMessages()` returns an empty array (0 rows), display "No messages yet — say hi!" instead of a blank container.

   - If `sendMessageToDb` returns an error, show a visible error message near the input bar (e.g., a red text "Failed to send. Check connection.").

4. **Disable button during send:**
   - When the user clicks Send, disable the send button (`button.disabled = true`).
   - Re-enable it after the database returns success or failure (in the `.finally` block).

```javascript
supabaseClient.auth.onAuthStateChange((event, session) => {
    if (event === 'SIGNED_IN' && session) {
        // Show chat, hide auth
    }
    if (event === 'SIGNED_OUT') {
        // Show auth, hide chat
        // Clear messages to avoid showing old data
    }
});
```

3. Add a **Logout button** somewhere in your UI (e.g., in the sidebar header or a profile section). On click, call `supabaseClient.auth.signOut()`.

### Task 2b.4 — Replace `username` With Real User ID

**Goal:** Every message is tied to the authenticated user's ID, not a typed-in name.

**Action Steps:**

1. **Database Migration:**
   - In the Supabase dashboard, add a new column to `messages`: `user_id` (`uuid`, nullable for now).
   - Backfill existing rows: you can leave `user_id` null for old test rows, or delete them (recommended: delete old rows and start fresh).

2. **Update `sendMessageToDb`:**
   - Get the current user: `const user = supabaseClient.auth.getUser()` or from the session object you store globally.
   - Change the insert call to include `user_id: user.id` instead of `username: 'Guest'`.
   - For now, keep `username` as a display name fallback (you can use `user.email` as the display name, e.g., `user.email.split('@')[0]`).

3. **Update Bubble Rendering:**
   - When rendering messages, you now have a `user_id` in the data.
   - Compare `message.user_id` to the current logged-in user's `user.id`.
   - If they match → render as `sent` (green, right-aligned).
   - If they don't match → render as `received` (grey, left-aligned).
   - Show the display name or email prefix above/beside the bubble so you know who sent it.

4. **Update `fetchMessages`:** Select `user_id` and `username` (or just `user_id` and join with a profiles table later — for now, store email as fallback).

5. **Delete or ignore old test messages** that don't have a `user_id`.

**Verification (MANDATORY):**
- [ ] Log in as User A. Send a message. It appears as "sent" (green, right).
- [ ] Open incognito, log in as User B. User A's message appears as "received" (grey, left).
- [ ] User B sends a message. In User A's window, User B's message appears as "received".
- [ ] The database `user_id` field is correctly populated for every new message.
- [ ] No `username` field is used for identity anymore (it can be removed or repurposed).

**If this fails →** Check that you're correctly retrieving the current user's ID from the session. Ensure the `insert` includes `user_id`.

## Debugging Tips for This Version

| Problem | Likely Fix |
| :--- | :--- |
| Signup fails with "User already registered" | Use a different email or delete the user from the dashboard. |
| Login fails with "Invalid login credentials" | Check password spelling. Use the "Forgot password" flow if needed. |
| Realtime events stop working | Check Replication settings in the dashboard. Ensure the channel is subscribed. |
| Duplicate bubbles on send | You're rendering optimistically AND the realtime event is firing. Use Option A (realtime only) from Task 2a.4. |
| `user_id` is `null` in the database | You're not passing `user_id` in the insert. Get the user ID from `supabaseClient.auth.getUser()` or stored session. |
| Sent messages appear as "received" | You're comparing `user_id` incorrectly. Log both IDs to the console to debug. |
